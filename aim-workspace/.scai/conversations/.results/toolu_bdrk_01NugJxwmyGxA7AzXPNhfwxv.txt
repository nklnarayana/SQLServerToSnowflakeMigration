76... ### 5.1 Business use cases
77... 
78... Waves need nothing from the user. Business use cases always run, after the other analyses.
79... `scai assessment waves` assigns every deployable object a wave number and rank
80... in category packs of about 100–200 objects. Use cases stay a catalog until a
81... later change rewrites waves for a selected use case. **Do not ask for a wave size, prioritization
82... patterns or a wave ordering.** An `assessment_options` value from an older
83... session may still carry `custom_wave_size`, `prioritize` or
84... `dependency_order`; ignore those tokens.
85... 
86... The converted code alone produces a catalog. Three optional inputs make it more
87... complete by showing what runs and what is read, so use cases are confirmed
88... instead of proposed from structure: the scheduler that runs the ETL, SQL Server
89... Agent jobs, and query logs. Ask each question that applies once, with the other
90... input questions. They are optional: never block the assessment on them, never
91... search for files, and never answer for the user. Skipping, or choosing later, is
92... not a failure: the report lists the input as not provided and says what it would
93... add.

96... Never copy, rename or move it under the project, and do not read it here: the
97... business use cases agent reads it in place. Do not repeat these questions

302... #### 5.7a `later` on SQL Server
303... 
304... Do not ask for a database name or number of days. Show this review guidance,
305... then paste
306... `workload-insights/references/create-extended-events-session.sql` unchanged:
307... 
308... > **Review the capture before running it.** SQL Server keeps no history of past
309... > queries, so nothing can be reported until a capture is running. This starter
310... > script creates a **SQL Server Extended Events** session for one database, but
311... > leaves it stopped. While it runs, it records each completed user statement
312... > and stored-procedure call that meets the duration filter — duration, CPU,
313... > reads, writes, rows, application, and user — plus errors at severity 11 or
314... > higher. Statement text is used only to classify the query type. Review every
315... > value, replace `YourDatabase` in all three predicates, and uncomment
316... > `STATE = START` only when you are ready to begin. The three events and their
317... > `ACTION` lists must stay or the report loses columns.
318... >
319... > **A DBA should own this capture.** Have a DBA set the values, confirm it is
320... > safe to run on this instance, and start it. Watch the server once it is
321... > running — CPU, disk space, and waits — and stop the session if anything
322... > degrades.
323... >
324... > This capture uses CPU and disk. It is reasonable on a typical host with the
325... > defaults below, but it is not free and can compete with the database if the
326... > settings are too aggressive. Do not switch `EVENT_RETENTION_MODE` to
327... > `NO_EVENT_LOSS` — that can stall user queries.
328... >
329... > **You can change these to fit the capture:**
330... >
331... > - **Session name** — default is `WorkloadReport_XE`. Change it if another
332... >   session already uses that name; keep the same name in create/start/stop.
333... > - **Duration threshold** — default is 0.5 seconds
334... >   (`[duration] >= 500000`, microseconds). Raise it to write less; lowering it
335... >   captures more and costs more CPU and disk.
336... > - **Filters** — default is one database, no system work, no SSMS/telemetry,
337... >   and errors at severity 11 or higher. Removing the database predicate traces
338... >   the whole instance and is usually too wide.
339... >
340... > **Set these carefully — they affect the database:**
341... >
342... > - **`filename`** — replace `<dedicated volume>` with a path on a volume that
343... >   has space and is not a data or log disk.
344... > - **`max_file_size`** (200 MB) and **`max_rollover_files`** (5) — together
345... >   cap disk at 1 GB. Confirm more than that is free before starting.
346... > - **`MAX_MEMORY`** (8,192 KB) — how much RAM the session may hold.
347... > - **`MAX_DISPATCH_LATENCY`** (30 seconds) — how soon events flush to disk.
348... > - **`STARTUP_STATE`** (OFF) — the session stays stopped after service restart.
349... > - **`MEMORY_PARTITION_MODE`** — unset for a typical host. On a busy many-core
350... >   server, consider `PER_CPU` and raise `MAX_MEMORY` to 16–32 MB first.
351... 
352... After the SQL, tell the user:
353... 
354... - `CREATE` leaves the session stopped; start it only when ready.
355... - Leave it under representative traffic. Around 30 days is useful, but a
356...   shorter window works.
357... - Copy every rollover `.xel`, then stop the session. Leaving it running
358...   continues to use CPU and disk.
359... - Re-run assessment, choose **I have the `.xel`**, and provide all files.
360... - This assessment continues now and does not wait for the capture.
361... 
362... Use skipped summary `capture SQL provided; re-run assessment with the .xel
363... files`. Do not model the capture as pending work or mention it again at
364... completion.
