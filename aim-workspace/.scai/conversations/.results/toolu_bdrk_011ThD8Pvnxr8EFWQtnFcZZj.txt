9...

30... ## Overview — Tell the User
31... 
32... Before starting any configuration, tell the user briefly, in your own words (a few sentences, not a quoted block), what Snowflake's Data Migration and Validation Framework is:
33... 
34... - A fault-tolerant, scalable two-part system: an **Orchestrator** that splits the work into parallel tasks, and one or more **Workers** that read from the source and upload to Snowflake.
35... - **Two independent placement choices** in Step 0: the orchestrator on **SPCS** (a Snowpark Container Services compute pool in their account, recommended for real migrations) or **local** (this machine, laptop / PoC only); each worker on **SPCS** (recommended whenever the source is reachable from Snowflake), their machine, other VMs or Kubernetes.
36... - They stay in control: which tables, partitioning, incremental or full loads, worker count, row filters and column remaps, stop and resume without losing progress. Nothing runs until they approve the configuration.
37... - The same infrastructure runs validation (schema, metrics and row level).
38... 
39... Mention the **metadata storage mode** only on an account without Hybrid Table support: the orchestrator falls back to standard/`TRANSIENT` metadata tables, which is correct but lowers task-queue throughput, so start with fewer workers ([Metadata storage mode reference](./references/metadata-storage-mode-reference.md); not the same as L3 "hybrid" row validation).
40... 
41... Placement is the user's choice: ask first, **recommend SPCS** for each when they have not chosen, and wait for their confirmation. Do not start infrastructure until they confirm.
42... 
43... **Always use the official tooling for data movement and validation.** Route table migration through `migrate_data` and validation through `validate_data`. Do not suggest ad-hoc extract/copy/compare scripts.
44... 
45... > **Supported sources**: SQL Server, Azure Synapse, Redshift, Oracle, Teradata, PostgreSQL, BigQuery, Snowflake (validation only)
46... > **Supported target**: Snowflake

48... ## Architecture
49... 
50... ```
51... ┌──────────────────┐     ┌──────────────────────────────────────┐
52... │  Customer Env     │     │         Snowflake Account             │
53... │  ┌─────────────┐ │     │  ┌────────────────────────────────┐  │
54... │  │  Worker(s)   │─┼─────┤  │  Orchestrator (SPCS)            │  │
55... │  └──────┬──────┘ │     │  │  → migration + validation tasks │  │
56... │         │ reads   │     │  └────────────────────────────────┘  │
57... │  ┌─────────────┐ │     │  ┌────────────────────────────────┐  │
58... │  │Source System │ │     │  │  Target Tables                  │  │
59... │  └─────────────┘ │     │  └────────────────────────────────┘  │
60... └──────────────────┘     └──────────────────────────────────────┘
61... ```
62... 
63... - **Orchestrator** runs on SPCS (requires a compute pool) or locally. Handles migration workflows (break into tasks, `COPY INTO`) and validation workflows (schema/metrics/row comparison).
64... - **Worker** runs on SPCS (recommended when the source is reachable from Snowflake), on this machine, on other VMs, or on Kubernetes. Reads from the source and uploads to a Snowflake stage (migration) or streams rows for comparison (validation). Not needed for most Iceberg migration strategies.
65... - **Snowflake-to-Snowflake validation runs in warehouse.** It uses the
66...   orchestrator but no Data Exchange Worker. Do not generate worker config,
67...   ask for worker placement, or start a worker for a Snowflake source project.
68... - **Direct (small SQL Server source only):** no orchestrator and no worker. `migrate_data` / `validate_data` move and check the data straight from this session with `scai --direct`. It is recorded as `data_orchestrator_placement: direct` and `data_worker_placement: direct` (Step 0.a), and every `data_infrastructure` mode then starts, stops and probes nothing.
69... - **The orchestrator + worker are shared, brought up ONCE, and reused across every `migrate_data` / `validate_data` dispatch** (migrate → validate → revalidate all run against the same infrastructure). Bring it up with `data_infrastructure(mode="up")` and tear it down with `data_infrastructure(mode="down")` (local) or [./teardown/SKILL.md](./teardown/SKILL.md) (SPCS). Dispatch does **not** start or resume infrastructure — if it is not up, `migrate_data` / `validate_data` return a `remediation` pointing back to `data_infrastructure(mode="up")`.
70... - **Whenever infrastructure starts**, tell the user that idle infrastructure can accrue Snowflake credits until teardown — the `data_infrastructure(mode="up")` response includes a `cost_reminder` field to relay.
71... - **An open question is not a pause.** Before the session waits on the user with no wave running (a confirmation, an EWI decision, an overnight gap), offer `data_infrastructure(mode="down")`; resume with `mode="up"`. See [Waiting on the user](./teardown/SKILL.md#waiting-on-the-user), and the one-time cost settings (pool `MIN_NODES = 1`, idle SPCS suspend, warehouse auto-suspend, rule-engine Cortex Search lag) in teardown Step 3.
72... - **Say what the pool costs from a fresh read.** A pool's state is stale minutes after you read it: an `IDLE` pool with no service suspends itself after its `AUTO_SUSPEND_SECS`. Before telling the user a pool is idle, billing, or worth suspending, re-run `DESCRIBE COMPUTE POOL <POOL>;` in that turn; never repeat a state from an earlier turn.

74... ## The `data_infrastructure` tool
75... 
76... Use the `data_infrastructure` tool (modes `up` / `down` / `status`) to manage the shared orchestrator + worker lifecycle — **pass `compute_pool` to run the orchestrator on SPCS, omit it for local**; `start_worker=false` skips the local worker (Iceberg / externally-managed workers). Call `up` once before dispatching migrations/validations. See the tool's own description for the full parameter list — don't restate it here.

78... ## Idempotency
79... 
80... **One project setting, not one choice per action.** The orchestrator/worker
81... placement selected in Step 0 is shared by migration and validation and remains
82... in effect until the user explicitly asks to change it. Do not re-ask local vs
83... SPCS when validation begins, and do not ask a per-object subagent to start,
84... stop, repair, or reconfigure infrastructure. Subagents only dispatch against
85... the setup already in place; if infrastructure is unavailable, they return the
86... remediation to the main agent.
87... 
88... If the user explicitly asks to change placement or a persisted data strategy,
89... the **main agent** owns that setup change. Re-enter this skill for placement or
90... worker changes, and load [`../setup/data-strategy/SKILL.md`](../setup/data-strategy/SKILL.md)
91... for migration/validation strategy changes. Complete the change once, persist
92... it, bring infrastructure up as needed, and only then resume per-object
93... dispatch.

95... **Recorded `direct`:** when `.scai/config/plugin.yml` records `data_orchestrator_placement: direct`, there is nothing to bring up. Skip the budget and pool shape checks and the bring-up below, tell the user "Data migration and validation run direct for this project (no orchestrator or worker), so there is no infrastructure to start.", and return to the caller. `migrate_data` / `validate_data(mode="run")` take the direct path by default. Move the project off `direct` only when the user asks: re-enter Step 0, then pass `compute_pool` (or `start_worker`) to `up`.
